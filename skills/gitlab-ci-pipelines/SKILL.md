# GitLab CI: как писать пайплайны

Скилл про устройство самого пайплайна: структура `.gitlab-ci.yml`, правила запуска, граф зависимостей, кэш и артефакты,
переиспользование, безопасность. Работа с уже запущенными пайплайнами (логи, ретраи, статусы через `glab`) сюда не
входит.

## Шаг 0. Проверь glab

Проверка конфига, симуляция пайплайна и запросы к API GitLab идут через `glab`. Если есть доступ к терминалу, начни с
этого шага (в чате без терминала пропусти его):

```bash
glab --version       # установлен ли
glab auth status     # авторизован ли на хосте текущего репозитория
```

- **glab не установлен.** Скажи пользователю и предложи установить (macOS: `brew install glab`, остальные способы в
  README проекта `gitlab-org/cli`). Ставь сам только с его согласия. Без glab работу продолжай, но валидацию через
  GitLab заменяй проверкой синтаксиса YAML и прямо пиши, что lint не запускался.
- **Не авторизован.** Внутри репозитория glab берёт хост из git remote, поэтому self-hosted инстанс подхватывается сам.
  Авторизация через personal access token со scope `api`: попроси пользователя создать токен в профиле GitLab (Personal
  access tokens) и выполнить у себя `glab auth login --hostname <host>`, выбрав вход по токену. Токен он вводит сам: не
  проси вставлять его в чат и не передавай через `--token` в командной строке, иначе токен останется в истории shell.
- **Ошибка сертификата (x509) на self-hosted с внутренним CA.** `glab config set ca_cert /path/to/ca.pem --host <host>`.
  `skip_tls_verify true` годится только как временная мера и с согласия пользователя.
- **Работа вне репозитория.** Хост указывай явно: `GITLAB_HOST=<host> glab ... -R group/project` или один раз
  `glab config set -g host <host>`.

## Прежде чем писать YAML

Собери контекст, от него зависит половина решений.

1. **Версия и редакция GitLab.** Компоненты, `spec:inputs`, `workflow:auto_cancel`, `retry:exit_codes` появились в
   разных версиях, часть возможностей есть только в Premium (merge trains, protected environments с approvals,
   `secrets:`). Если версия неизвестна, посмотри AGENTS.md или CLAUDE.md проекта, проверь `glab api version`
   или спроси. Пока версия не ясна, опирайся на базовые возможности и помечай, что требует
   свежего GitLab.
2. **Как устроен текущий пайплайн.** Прочитай `.gitlab-ci.yml` и всё, что он подключает через `include`. Особенно важно
   понять, где живут условия запуска (шаблоны правил в отдельном файле, общий репозиторий шаблонов, компоненты, правила
   прямо в джобах) и разнесены ли MR, релизные и ночные пайплайны по отдельным файлам или дочерним пайплайнам. Как
   искать, описано в [references/rules-and-workflow.md](references/rules-and-workflow.md), раздел «Сначала смотри, как
   устроено в проекте».
3. **Контекст проекта**: раннеры (`tags`), базовые образы, общие шаблоны, ветки и формат релизных тегов. Сначала ищи
   раздел про CI в AGENTS.md проекта (или в CLAUDE.md, если проект живёт на нём), потом в самом конфиге (`tags`,
   `image`, `include`, правила на теги). Чего нет, уточни у пользователя или явно назови допущение. Если раздела про CI
   нет или его не хватило, действуй по разделу «Контекст CI в AGENTS.md» ниже.
4. **Когда пайплайн должен запускаться.** Выпиши события: MR, пуш в основную ветку, тег, расписание, ручной запуск,
   триггер из другого проекта. Для каждого события определи набор джоб. Эта матрица потом превращается в
   `workflow:rules` и `rules` джоб.

## Порядок работы

1. **Спроектируй граф.** Перечисли джобы: что каждая получает на вход, что отдаёт (артефакты), от кого зависит. Дешёвые
   проверки (lint, статанализ, unit-тесты) стартуют сразу. Дорогие (сборки, UI-тесты, деплой) стартуют через `needs`,
   как только готовы их входы.
2. **Напиши YAML.** В существующем проекте повторяй его структуру и стиль. Новый пайплайн начинай
   с [assets/base.gitlab-ci.yml](assets/base.gitlab-ci.yml) и [assets/rules.yml](assets/rules.yml), раскладка по
   файлам и порядок ключей ниже.
3. **Проверь.** Минимум для любой правки — схема и `glab ci lint`. Если трогал правила запуска, `needs` или `include`,
   проверь ещё матрицу событий (`glab ci lint --dry-run` для пушей и тегов, `gitlab-ci-local --list` для MR и
   расписаний) и что MR-пайплайн не окажется пустым (`scripts/check_mr_pipeline_not_empty.py`). Уровни проверки, команды и их ограничения описаны в [references/testing.md](references/testing.md). Если
   ничего запустить не удалось, прямо скажи, что конфигурация не проверялась.
4. **Пройди чеклист** в конце файла.
5. **Отдай результат** в формате из раздела «Что отдавать пользователю».

## Раскладка по файлам

В существующем проекте повторяй его раскладку. Правило ниже действует для нового пайплайна и когда пользователь просит
навести порядок.

- **Шаблоны правил всегда в отдельном файле** `.gitlab/ci/rules.yml`, даже в маленьком проекте: так условия запуска
  лежат в одном предсказуемом месте, и их не приходится собирать по джобам.
- **Остальное в одном `.gitlab-ci.yml`**, пока выполнены оба условия: в проекте одна область (одно приложение или
  платформа) и файл не длиннее ~200 строк.
- **Разноси по `.gitlab/ci/<область>.yml`**, как только нарушено любое из условий: появилась вторая независимая область
  (frontend и backend, приложение и библиотека, сервис и документация) или файл перерос ~200 строк. Отдельным файлом идут и
  джобы, которые нужны только одному типу пайплайна (`release.yml`, `nightly.yml`).
- **Режь по областям.** Сборка, тесты и lint backend меняются вместе и живут в `backend.yml`. Разбиение по стадиям
  (`build.yml`, `test.yml`, `deploy.yml`) размазывает одну область по нескольким файлам, его не используй.
- Скрытые шаблоны, которыми пользуются несколько областей (`.docker-build`, `.deps-cache`), клади в `.gitlab/ci/templates.yml`;
  шаблоны одной области держи в её файле.
- После разнесения в корневом `.gitlab-ci.yml` остаются только `include`, `workflow`, `stages`, `variables` и
  `default`, без джоб.
- Для разнесения по файлам хватает `include: local`. Дочерние пайплайны нужны, когда требуется изоляция: свои стадии,
  условный запуск большого набора джоб (см. [references/child-pipelines.md](references/child-pipelines.md)).

```text
.gitlab-ci.yml        # include, workflow, stages, variables, default
.gitlab/ci/
  rules.yml           # шаблоны правил
  templates.yml       # скрытые джобы, общие для нескольких областей
  backend.yml         # сборка, тесты, lint backend
  frontend.yml
  release.yml         # публикация и деплой
```

Порядок ключей внутри файла:

```yaml
include: [ ]          # шаблоны правил, файлы областей, общие шаблоны, компоненты
workflow: { }         # когда вообще создаётся пайплайн
stages: [ build, test, deploy ]  # крупные фазы для UI, порядок задаёт needs
variables: { }        # глобальные переменные, без секретов
default: { }          # image, tags, interruptible, retry, timeout
.template-name: { }   # скрытые шаблоны для extends, имя начинается с точки
job-name: { }         # джобы, сгруппированные по стадиям
```

**Комментарии.** Структуру файла передают порядок ключей, имена джоб и разбиение на файлы. Декоративные разделители вида
`# --- Переиспользуемые куски ----------` не добавляй: информации в них нет, при правках они расходятся с содержимым и
засоряют diff. Комментарий пиши, когда он объясняет неочевидное решение (почему из шаблона `main` исключены расписания,
почему у деплоя `interruptible: false`) или помечает TODO. Разделители, которые уже есть в проекте, не трогай, если не
правишь эти места.

## Принципы

### 1. Встраивайся в устройство проекта

Пайплайн живёт годами, его читают и правят люди, привыкшие к его структуре. Новые джобы подключай к существующим
шаблонам правил, клади в те же файлы и называй в том же стиле, даже если в этом скилле описан другой вариант. Если
структуру проекта стоит поменять, сделай задачу в текущем стиле, а предложение по рефакторингу дай отдельной строкой в
ответе.

### 2. Пайплайн создаётся только когда нужен

`workflow` в конфигурации проекта один и проверяется на каждое событие: он решает, будет ли пайплайн вообще, а `rules`
джоб решают, какие джобы в него попадут. Без `workflow:rules` пуш в ветку с открытым MR создаёт два пайплайна, branch и
MR, и раннеры делают работу дважды. Добавь `workflow:auto_cancel:on_new_commit: interruptible` и `interruptible: true`
для джоб без побочных эффектов, тогда новый коммит отменяет устаревший пайплайн. Подробности и объяснение модели для
пользователя в [references/rules-and-workflow.md](references/rules-and-workflow.md).

### 3. MR-пайплайн никогда не бывает пустым

Если правила с `changes` отсекают все джобы, GitLab не создаёт пайплайн. При включённой настройке «Pipelines must
succeed» такой MR нельзя смёржить: он висит в статусе «Checking pipeline status». Пайплайн, в котором остались только
джобы стадий `.pre` и `.post`, тоже не запускается. Поэтому в MR-пайплайне всегда нужна хотя бы одна джоба без условия
`changes` и не в `.pre`/`.post`: настоящая дешёвая проверка (lint) или отдельная джоба-заглушка (пример в
[references/rules-and-workflow.md](references/rules-and-workflow.md), раздел «rules:changes и его ловушки»). Каждый раз,
когда трогаешь `rules`, `changes`, `workflow` или `include`, запускай проверку
`python3 <папка скилла>/scripts/check_mr_pipeline_not_empty.py` из корня репозитория.
Папка скилла — каталог, где лежит этот SKILL.md; в зависимости от агента и способа установки это, например,
`~/.claude/skills/gitlab-ci-pipelines`, `~/.agents/skills/gitlab-ci-pipelines` или `.agents/skills/gitlab-ci-pipelines`
в проекте.

### 4. Условия запуска живут в именованных шаблонах

Используй `rules`; `only`/`except` больше не развиваются и не комбинируются с `rules`. Для нового проекта структура по
умолчанию такая: условия вынесены в шаблоны по событиям (`.rules-mr`, `.rules-main`, `.rules-release`, `.rules-nightly`)
в отдельном файле, джобы подключают их через `extends` (одно событие) или `!reference` (несколько событий). Когда наборы
джоб для разных событий сильно различаются, каждый тип пайплайна выносится в свой файл и запускается дочерним пайплайном
([references/child-pipelines.md](references/child-pipelines.md)). Вариант с типом пайплайна в переменной
(`PIPELINE_TYPE` из `workflow:rules:variables`) применяй, только если пользователь просит или так уже устроено в
проекте.

### 5. Порядок задаёт `needs`, стадии группируют

Со `stages` джоба ждёт окончания всей предыдущей стадии, то есть самой медленной джобы в ней. С `needs` она стартует
сразу после своих зависимостей, и пайплайн становится графом (DAG). `needs: []` означает старт немедленно. Подробности и
параллелизм в [references/jobs-and-dag.md](references/jobs-and-dag.md), дочерние и multi-project пайплайны
в [references/child-pipelines.md](references/child-pipelines.md).

### 6. Артефакты передают результат, кэш ускоряет

Артефакт гарантированно доезжает до джоб, которые его ждут. Кэш работает по принципу best effort: его может не
оказаться, он может лежать на другом раннере или прийти от другой ветки. Всё, без чего следующая джоба упадёт, передавай
артефактом; кэшируй зависимости (npm, pip, Go-модули, Maven). У артефактов всегда задавай `expire_in`. Подробности
в [references/cache-and-artifacts.md](references/cache-and-artifacts.md).

### 7. У каждого куска конфигурации одно место

Общие куски выноси в скрытые джобы с `extends`, точечные фрагменты подтягивай через `!reference`, между репозиториями
используй `include: project` с зафиксированным `ref` или CI/CD-компоненты с версией. YAML-якоря работают только внутри
одного файла. Подробности в [references/reuse.md](references/reuse.md); подключение конфигов из других репозиториев,
версии, права доступа и проверка изменений в общих шаблонах
в [references/includes-and-components.md](references/includes-and-components.md).

### 8. Логика живёт в репозитории, YAML её вызывает

Если в `script` больше 5–10 строк shell, вынеси их в `scripts/ci/*.sh` с `set -euo pipefail`, в задачу сборочной системы
(Makefile, npm-скрипт, задача Maven) или в утилиту. Такой код можно запустить локально, протестировать и нормально прочитать в ревью.
YAML отвечает на вопросы «когда» и «где», скрипт отвечает на «что».

### 9. Воспроизводимость

Образы указывай с конкретным тегом (лучше digest), без `latest`. `include: project` и компоненты фиксируй тегом или SHA.
Версии инструментов держи в образе или в репозитории, чтобы один и тот же коммит собирался одинаково через месяц.

### 10. Быстрая обратная связь

- Дешёвые проверки стартуют первыми и ничего не ждут (`needs: []`).
- `rules:changes` отсекает тяжёлые джобы при нерелевантных изменениях; в branch-пайплайнах добавляй `compare_to`.
- `parallel` и `parallel:matrix` шардируют тесты и раскладывают матрицу сборок.
- `timeout` на джобу подбирай под её реальное время, чтобы зависшая джоба не держала раннер час.
- `retry` ставь только на инфраструктурные причины (`runner_system_failure`, `api_failure`), иначе ретраи маскируют
  флаки.

### 11. Секреты живут вне YAML

Используй CI/CD-переменные (protected + masked) или внешнее хранилище через `id_tokens` (OIDC). Не печатай секреты в лог
и не включай `set -x` рядом с ними. Подробности в [references/security.md](references/security.md).

## Чеклист перед тем как отдать

- [ ] Изменения встроены в структуру проекта: правила взяты из его шаблонов, файлы и имена в его стиле.
- [ ] Новый пайплайн разложен по файлам по правилу из раздела «Раскладка по файлам»; в существующем повторена раскладка
  проекта.
- [ ] Есть `workflow:rules`, branch и MR пайплайны не дублируются, и `workflow` пропускает все события, под которые есть
  джобы.
- [ ] Для каждого события из матрицы понятно, какие джобы запустятся, и проверено, что лишние не запустятся (в том числе
  что ночной пайплайн на основной ветке не цепляет джобы `main`).
- [ ] Нет `only`/`except`; несколько шаблонов правил объединены через `!reference` (при `extends` выживают правила
  последнего шаблона).
- [ ] Зависимости выражены через `needs`; джобы, которым не нужны чужие артефакты, их не скачивают.
- [ ] Результаты сборки передаются артефактами с `expire_in`; у кэша осмысленный `key`, а джобы, которые только читают
  кэш, используют `policy: pull`.
- [ ] Отчёты тестов (`artifacts:reports:junit`) сохраняются с `when: always`.
- [ ] Образы, внешние `include` и компоненты зафиксированы тегом или SHA; ни один `ref` не указывает на ветку шаблона.
- [ ] У триггер-джоб дочерних и multi-project пайплайнов есть `strategy: mirror` (или `depend` на старых версиях
  GitLab); правила внутри дочерних пайплайнов не опираются на `merge_request_event`.
- [ ] Джобы не скопированы друг с друга: общее вынесено в `extends`, `!reference` или компонент.
- [ ] Длинная логика вынесена из `script` в файлы репозитория.
- [ ] Нет декоративных комментариев-разделителей; комментарии объясняют только неочевидные решения.
- [ ] У джоб есть `timeout`; `interruptible: true` стоит только там, где джобу безопасно прервать (деплой и публикация к
  ним не относятся).
- [ ] У деплойных джоб есть `environment`, `resource_group`, и они запускаются только с защищённых веток или тегов.
- [ ] В YAML нет секретов, `set -x` и verbose-режимы не выводят переменные.
- [ ] В MR-пайплайне при любых изменениях есть хотя бы одна джоба вне `.pre`/`.post`:
  `scripts/check_mr_pipeline_not_empty.py` завершился с OK.
- [ ] Пройдены проверки из [references/testing.md](references/testing.md) (минимум схема и lint), или в ответе прямо
  сказано, что не проверялось.

Типичные ошибки и способы их исправить собраны в [references/anti-patterns.md](references/anti-patterns.md), он же
пригодится для ревью чужого пайплайна.

## Что отдавать пользователю

1. YAML: файл целиком для нового пайплайна или diff для точечной правки.
2. Матрицу запуска, какие джобы в каком событии появляются:

   | Джоба | MR | основная ветка | тег | расписание |
      |---|---|---|---|---|
   | lint | ✓ | ✓ | – | – |
   | build | ✓ | ✓ | ✓ | – |

3. Неочевидные решения одной строкой каждое и то, что нужно сделать вне YAML: завести переменную, добавить тег раннеру,
   защитить ветку или environment.
4. Что проверено и что нет, в формате из [references/testing.md](references/testing.md), раздел «Что писать в ответе».

## Контекст CI в AGENTS.md

Скилл не привязан к проекту: раннеры, раскладку файлов, шаблоны правил и прочую специфику он берёт из AGENTS.md (или
CLAUDE.md) проекта и из самого конфига.

Если раздела про CI в AGENTS.md нет или в нём не хватило того, что пришлось выяснять по файлам или спрашивать, в конце
ответа предложи его дописать:

- покажи готовый фрагмент только с фактами, которые подтвердились в этой задаче, без заглушек и догадок;
- спроси, добавить ли его, и записывай только после согласия: в AGENTS.md, или в CLAUDE.md, если проект живёт на нём;
- если пользователь отказался, в этом разговоре больше не предлагай.

Что обычно стоит записать: версию и редакцию GitLab; раскладку конфига (корневой файл, шаблоны правил, файлы областей);
типы пайплайнов и чем они различаются (MR, основная ветка, релизный тег, расписания и их переменные); теги раннеров и для
каких джоб они; подключаемые общие шаблоны и компоненты и как фиксируются их версии; ограничения (что нельзя запускать
из MR, что только вручную).

```markdown
## CI

- GitLab 17.x self-managed, Premium; glab по personal access token
- Правила в `.gitlab/ci/rules.yml` (`.rules-mr`, `.rules-main`, `.rules-release`), джобы по областям в `.gitlab/ci/`
- Релиз — тег `vX.Y.Z`; ночной прогон — расписание с `SCHEDULE_TYPE=nightly`
- Раннеры: `docker` для обычных джоб, `gpu` для тестов моделей
- Общие шаблоны: `platform/ci-templates` через `include: project`, `ref` на тег
```
