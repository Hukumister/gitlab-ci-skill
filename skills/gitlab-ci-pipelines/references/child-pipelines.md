## Когда нужен downstream-пайплайн

| Ситуация                                                                       | Что взять                                                                                                                  |
|--------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------|
| в монорепозитории независимые части со своим набором джоб                      | дочерний пайплайн на часть, запуск по `changes`                                                                            |
| у MR, релиза и ночного прогона сильно разные наборы джоб                       | дочерний пайплайн на тип события (см. [rules-and-workflow.md](rules-and-workflow.md), «Отдельный пайплайн на тип события») |
| набор джоб вычисляется скриптом (модули по impact analysis, матрица окружений) | динамический дочерний пайплайн                                                                                             |
| нужно запустить пайплайн другого проекта (e2e, деплой, обновление зависимых)   | multi-project                                                                                                              |
| в файле просто много джоб                                                      | downstream не нужен: разнеси файл через `include: local`                                                                   |

Дочерний пайплайн работает в том же проекте, на том же ref и коммите, что и родитель, и не показывается в общем списке
пайплайнов проекта. Multi-project пайплайн запускается в другом проекте, на ref, который выбираешь ты, и виден в списке
пайплайнов того проекта.

## Parent-child: базовый вариант

```yaml
frontend:
  trigger:
    include: .gitlab/ci/frontend.yml
    strategy: mirror
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      changes:
        - frontend/**/*
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

- В `trigger:include` можно передать до трёх файлов. Источники: `local`, `project` (с `ref` и `file`), `template` и
  `artifact` (с `job`) для сгенерированных файлов.
- Триггер-джоба — обычная джоба без `script`: к ней применимы `rules`, `needs`, `stage`, `when: manual`,
  `allow_failure`. Правила на триггер-джобу оформляй так же, как остальные правила в проекте.
- Дочерний файл — самостоятельная конфигурация: свои `stages`, `default`, `include`. Глобальные настройки родителя
  (`default`, шаблоны правил, подключённые файлы) туда сами не попадают; нужное подключи в дочернем файле через
  `include`.

## Статус триггер-джобы: strategy

- Без `strategy` триггер-джоба становится зелёной сразу после создания дочернего пайплайна. Родитель не ждёт результата,
  и пайплайн MR может быть зелёным при упавших дочерних тестах.
- `strategy: mirror` (свежие версии GitLab): статус триггер-джобы всегда совпадает со статусом дочернего пайплайна.
  Документация рекомендует его.
- `strategy: depend`: триггер-джоба ждёт дочерний пайплайн и берёт его статус, но в отдельных случаях статусы могут
  расходиться. Используй, если инстанс не поддерживает `mirror` (версию покажет `glab api version`).
- Отчёты дочерних джоб (JUnit, code quality и другие) попадают в виджет MR, только если у триггер-джобы есть `mirror`
  или `depend`.

## Правила внутри дочернего пайплайна

- `CI_PIPELINE_SOURCE` в дочернем пайплайне всегда `parent_pipeline`. Шаблоны правил на `merge_request_event` (вроде
  `.rules-mr`) там не сработают, и джобы молча исчезнут.
- Переменные `CI_MERGE_REQUEST_*` родителя передаются в дочерний пайплайн, поэтому MR-условие внутри дочернего пишется
  через них:

```yaml
.child-rules-mr:
  rules:
    - if: $CI_MERGE_REQUEST_ID

lint-frontend:
  extends: .child-rules-mr
  script:
    - ./scripts/ci/lint-frontend.sh
```

- Если дочерний файл запускается только для своего события (как в схеме «пайплайн на тип события»), правила по событию
  внутри не нужны вовсе.
- Для дочерних файлов заведи отдельные шаблоны правил рядом с основными, по тем же соглашениям об именах, и подключай их
  в дочерних файлах.

## Переменные

- `variables` триггер-джобы передаются в дочерний пайплайн. Там они считаются переменными триггера и имеют наивысший
  приоритет, то есть перекрывают значения из настроек проекта.
- `trigger:forward:yaml_variables` (по умолчанию `true`) передаёт переменные из YAML: глобальные и триггер-джобы.
- `trigger:forward:pipeline_variables` (по умолчанию `false`) передаёт переменные самого пайплайна: заданные при ручном
  запуске, в расписании, через API. Без этого дочерний пайплайн, например, не увидит `SCHEDULE_TYPE` из расписания:

```yaml
nightly:
  extends: .rules-nightly
  trigger:
    include: .gitlab/ci/nightly.yml
    strategy: mirror
    forward:
      pipeline_variables: true
```

- CI/CD-переменные из настроек проекта дочернему пайплайну доступны и так: проект тот же.

## Артефакты между родителем и дочерним

Из родителя в дочерний: передай ID родительского пайплайна переменной и сошлись на джобу через `needs:pipeline`:

```yaml
build:
  script:
    - ./scripts/ci/build.sh
  artifacts:
    paths:
      - build/output/
    expire_in: 1 day

e2e-tests:
  needs: [ build ]
  variables:
    PARENT_PIPELINE_ID: $CI_PIPELINE_ID
  trigger:
    include: .gitlab/ci/e2e-tests.yml
    strategy: mirror
```

```yaml
# .gitlab/ci/e2e-tests.yml
ui-tests:
  needs:
    - pipeline: $PARENT_PIPELINE_ID
      job: build
  script:
    - ./scripts/ci/ui-tests.sh
```

Из дочернего в родитель штатного способа забрать артефакты нет. Если результат дочернего пайплайна нужен дальше в
родителе, это повод пересмотреть разбиение: перенести потребителя в дочерний пайплайн или публиковать результат во
внешнее хранилище (package registry).

## Динамические дочерние пайплайны

Подходит, когда набор джоб вычисляется: модули, затронутые изменением (impact analysis), матрица окружений, список
сервисов.

```yaml
generate-pipeline:
  script:
    - ./scripts/ci/generate-pipeline.py --base "$CI_MERGE_REQUEST_DIFF_BASE_SHA" > generated.yml
  artifacts:
    paths:
      - generated.yml
    expire_in: 1 day

run-generated:
  needs: [ generate-pipeline ]
  trigger:
    include:
      - artifact: generated.yml
        job: generate-pipeline
    strategy: mirror
```

- Генератор — обычный код в репозитории (Python, Go): детерминированный, с unit-тестами. Шаблонизировать YAML через
  `sed` и `echo` не стоит.
- Если генератор может не найти ни одной задачи, пусть он выдаёт одну пустую джобу (`script: echo "nothing to do"`).
  Конфигурация без видимых джоб не создаст дочерний пайплайн, и триггер-джоба упадёт.
- Проверяй сгенерированный файл схемой или `glab ci lint` прямо в джобе-генераторе, чтобы ошибка была видна там, а не в
  виде непонятного падения триггера (см. [testing.md](testing.md)).
- Размер артефакта с конфигурацией ограничен настройками инстанса.

## Multi-project пайплайны

```yaml
trigger-e2e:
  trigger:
    project: qa/e2e-tests
    branch: main
    strategy: mirror
  variables:
    APP_VERSION: $CI_COMMIT_SHORT_SHA
```

- У пользователя, который запускает верхний пайплайн, должно быть право запускать пайплайны в нижнем проекте. Иначе
  нижний пайплайн не стартует.
- В нижнем пайплайне `CI_PIPELINE_SOURCE` равен `pipeline`; его правила должны это учитывать.
- `branch` — ref нижнего проекта; правила защищённых веток и переменных действуют там по его настройкам.
- Артефакты верхнего пайплайна нижний забирает через `needs:project` (`job`, `ref`, `artifacts: true`; Premium). Для
  этого нужна роль не ниже Reporter и разрешение в allowlist job token.

## Ограничения

- Не больше двух уровней вложенности дочерних пайплайнов (родитель → дочерний → внучатый).
- Во всей иерархии по умолчанию не больше 1000 downstream-пайплайнов.
- До трёх файлов в одном `trigger:include`.
- У multi-project пайплайнов ограничения вложенности нет, поэтому следи, чтобы проекты не запускали друг друга по кругу.

## Отладка

- Ошибка в дочерней конфигурации видна на триггер-джобе родителя: «downstream pipeline can not be created» с причиной.
- Дочерний файл линтуй отдельно: `glab ci lint .gitlab/ci/frontend.yml`. Lint проверяет его как корневую конфигурацию,
  поэтому правила на `parent_pipeline` и `CI_MERGE_REQUEST_ID` так не проверить.
- Какие джобы появятся в дочернем пайплайне, проверь локально:
  `gitlab-ci-local --file .gitlab/ci/frontend.yml --list --variable CI_PIPELINE_SOURCE=parent_pipeline --variable CI_MERGE_REQUEST_ID=1`
  (подробнее в [testing.md](testing.md)).
- Перезапуск триггер-джобы пересоздаёт дочерний пайплайн целиком; упавшие джобы внутри можно перезапустить и по
  отдельности со страницы дочернего пайплайна.
