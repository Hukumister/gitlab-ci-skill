## Какие бывают внешние зависимости

| Способ               | Что подключает                              | Когда выбирать                                                  |
|----------------------|---------------------------------------------|-----------------------------------------------------------------|
| `include: project`   | YAML-файлы из другого проекта на инстансе   | внутренние шаблоны команды, с `spec:inputs` или без             |
| `include: component` | компонент с объявленными входами и версиями | блок для многих проектов, нужен явный контракт входов и каталог |
| `include: remote`    | файл по URL                                 | только доверенные источники вне инстанса, вместе с `integrity`  |
| `include: template`  | шаблоны, которые поставляются с GitLab      | редко: их содержимое меняется вместе с версией GitLab           |

Прежде чем добавлять новую зависимость, посмотри, что проект уже подключает и откуда (все `include` в корневом и
подключённых файлах), и используй то же.

## include: project

```yaml
include:
  - project: platform/ci-templates
    ref: v3.2.0
    file:
      - /templates/node.yml
      - /templates/rules.yml
```

- Без `ref` берётся HEAD шаблонного проекта: любой коммит туда сразу меняет пайплайны всех потребителей. Фиксируй тег
  или SHA.
- Вложенный `include: local` внутри подключённого файла ищется в проекте, где лежит этот файл, а не в твоём. Поэтому
  шаблонный репозиторий может раскладывать себя по нескольким файлам.
- Если шаблон объявляет `spec:inputs`, значения передаются через `include:inputs` (строки, числа, булевы):

```yaml
include:
  - project: platform/ci-templates
    ref: v3.2.0
    file: /templates/npm-test.yml
    inputs:
      project_dir: packages/api
```

## CI/CD-компоненты

```yaml
include:
  - component: $CI_SERVER_FQDN/platform/ci-components/npm-test@1.4.2
    inputs:
      name: api
      project_dir: packages/api
```

- Адрес: `<хост>/<путь проекта>/<имя компонента>@<версия>`. Хост бери из `$CI_SERVER_FQDN`, чтобы не хардкодить адрес
  инстанса.
- Версия может быть SHA коммита, тегом (semver), веткой, частичной версией (`1.4` — последняя `1.4.*`, `1` — последняя
  `1.*.*`) или `~latest`. Частичные версии и `~latest` работают только для компонентов, опубликованных в CI/CD Catalog;
  пре-релизы они не выбирают.
- Фиксируй полный тег или SHA. Частичную версию бери, только если команда договорилась автоматически получать патчи, а
  `~latest` не используй.
- Проект компонентов: каталог `templates/` в корне, компонент — `templates/<имя>.yml` или
  `templates/<имя>/template.yml`. Все компоненты проекта версионируются вместе (до 100 на проект); если компоненту нужна
  своя версия, его выносят в отдельный проект.

Компонент описывает входы в заголовке и использует их через `$[[ inputs.имя ]]`:

```yaml
spec:
  inputs:
    stage:
      default: test
    name:
      description: Суффикс имени джобы, например api
    project_dir:
      default: "."
      description: Каталог пакета относительно корня репозитория
    node_version:
      default: "22"
      options: [ "20", "22" ]
---
"npm-test-$[[ inputs.name ]]":
  stage: $[[ inputs.stage ]]
  image: registry.example.com/ci/node-$[[ inputs.node_version ]]:1.0.0
  script:
    - cd "$[[ inputs.project_dir ]]"
    - npm ci
    - npm test
```

- Входы подставляются при создании пайплайна, переменные (`$VAR`) раскрываются при выполнении джобы. Поэтому входами
  параметризуют имена джоб, стадии и ключи, которые переменной не задать.
- У входов есть `type` (`string`, `number`, `boolean`, `array`), `default`, `options`, `regex`, `description`; ошибка во
  входах видна сразу при создании пайплайна.
- Секреты и значения из настроек проекта передавай CI/CD-переменными, входы для этого не подходят.

Чего избегать автору компонента:

- глобальных ключей (`default`, глобальных `variables`, `workflow`): они растекаются по всему пайплайну потребителя;
- захардкоженного адреса инстанса и API: есть `$CI_SERVER_FQDN` и `$CI_API_V4_URL`;
- неявных зависимостей: образы и подключаемые файлы внутри компонента тоже фиксируй по версии.

## Как внешний конфиг сливается с локальным

- Слияние глубокое: словари сливаются на любой глубине, при конфликте простых значений побеждает файл, подключённый
  позже, а корневой `.gitlab-ci.yml` побеждает всех.
- Массивы (`rules`, `script`, `needs`, `tags`) не сливаются: значение из корневого файла заменяет массив целиком.
  Добавить одно правило к джобе из шаблона нельзя, только переписать `rules` полностью.
- Один и тот же файл можно подключить несколько раз; действует последнее подключение.
- `!reference` на джобы из подключённых файлов работает, YAML-якоря — нет.

Поменять джобу из шаблона можно, объявив в своём файле джобу с тем же именем и только изменёнными ключами:

```yaml
include:
  - project: platform/ci-templates
    ref: v3.2.0
    file: /templates/node.yml

npm-test:
  timeout: 45m
```

Это хрупко: если в новой версии шаблона джобу переименуют, твоя «правка» станет отдельной неполной джобой, и пайплайн
упадёт на создании. Если шаблон даёт скрытую джобу (`.npm-test`), надёжнее наследоваться от неё через `extends` и
держать свою джобу целиком у себя.

## Версии и обновление

- Обновление `ref` или версии компонента делай отдельным MR в проекте-потребителе: это и есть точка ревью изменений
  шаблона.
- Перед обновлением посмотри, что поменялось: diff шаблонного репозитория между тегами и итоговую конфигурацию до и
  после (ниже).
- Если в команде есть Renovate, он умеет поднимать `ref` в `include: project` (менеджер `gitlabci-include`).
- Ломающие изменения в шаблоне — новая мажорная версия; старую мажорную держи, пока потребители не переехали.

## Как увидеть, что реально подключилось

- `glab ci config compile` печатает итоговую конфигурацию: все `include` раскрыты, `extends` развёрнуты.
- `gitlab-ci-local --preview` делает то же локально и раскрывает `!reference`.
- Pipeline editor → вкладка Full configuration, или поле `merged_yaml` в ответе CI Lint API.

Сравнить итоговую конфигурацию до и после правки `ref` или версии компонента:

```bash
git show HEAD:.gitlab-ci.yml > /tmp/before-src.yml
glab ci config compile /tmp/before-src.yml > /tmp/before.yml
glab ci config compile > /tmp/after.yml
diff /tmp/before.yml /tmp/after.yml
```

## Права доступа

- Для приватного проекта в `include: project` у пользователя, который запускает пайплайн, должна быть роль не ниже
  Reporter в шаблонном проекте; для internal-проекта хватает любого внутреннего пользователя. Иначе пайплайн не
  создастся с ошибкой «not found or access denied».
- Пайплайн запускает тот, кто запушил, открыл MR или владеет расписанием. Поэтому без доступа к шаблонам пайплайн может
  сломаться только у одного разработчика или только у ночного расписания.
- `include: remote` скачивается по HTTP (S) без авторизации, поэтому годится только для публично доступных файлов.

## Как менять общий шаблон или компонент

Изменение общего шаблона сразу затрагивает всех потребителей, которые на него обновятся, поэтому проверяй до выпуска
тега.

1. **Self-test в репозитории шаблонов.** Корневой `.gitlab-ci.yml` проекта компонентов подключает собственный компонент
   на текущем коммите и проверяет результат:

```yaml
include:
  - component: $CI_SERVER_FQDN/$CI_PROJECT_PATH/npm-test@$CI_COMMIT_SHA
    inputs:
      name: sample
      project_dir: tests/sample-app

check-npm-test:
  needs: [ npm-test-sample ]
  script:
    - ./scripts/ci/check-test-reports.sh

create-release:
  image: registry.example.com/ci/release-cli:1.0.0   # TODO: образ с release-cli, принятый в команде
  rules:
    - if: $CI_COMMIT_TAG =~ /^\d+\.\d+\.\d+$/
  script:
    - echo "Release $CI_COMMIT_TAG"
  release:
    tag_name: $CI_COMMIT_TAG
    description: Release $CI_COMMIT_TAG
```

Для шаблонов через `include: project` идея та же: репозиторий шаблонов подключает свои файлы через `include: local` и
гоняет на них тестовые джобы или пайплайн тестового проекта.

2. **Проверка на реальном потребителе.** В ветке проекта-потребителя временно укажи `ref` (или `@` у компонента) на
   ветку или SHA шаблона, прогони пайплайн и сравни итоговую конфигурацию. Перед мёржем верни ссылку на тег:
   потребитель, смёрженный со ссылкой на ветку, начнёт получать все будущие изменения шаблона без ревью.
3. **Выпуск.** Тег по semver. Чтобы компонент появился в CI/CD Catalog, релиз создаётся джобой с ключом `release` на
   теге (как `create-release` выше); проект при этом должен быть отмечен как каталожный.

## Типичные ошибки

| Ошибка                                                      | Чем плохо                                                     | Как исправить                                                  |
|-------------------------------------------------------------|---------------------------------------------------------------|----------------------------------------------------------------|
| `include: project` без `ref` или с `ref: main`              | изменение шаблона ломает всех сразу и без ревью               | тег или SHA                                                    |
| Потребитель смёржен с `ref` на ветку шаблона после проверки | будущие изменения приезжают без ревью                         | вернуть тег перед мёржем                                       |
| Добавили `rules` к джобе из шаблона, ожидая слияния         | массив заменяется, правила шаблона пропадают                  | переписать `rules` целиком или наследоваться от скрытой джобы  |
| Переопределение видимой джобы шаблона по имени              | после переименования в шаблоне остаётся неполная джоба        | `extends` от скрытой джобы шаблона                             |
| Компонент задаёт `default` или глобальные `variables`       | меняет поведение всего пайплайна потребителя                  | настройки на уровне джоб компонента                            |
| `include:rules` на переменных из `variables` в YAML         | такие переменные там недоступны, условие не срабатывает       | предопределённые переменные или переменные проекта и пайплайна |
| Приватный шаблон без доступа у части пользователей          | «not found or access denied» у отдельных людей или расписаний | выдать Reporter или сделать проект internal                    |
