## Секреты

- Секреты хранятся в CI/CD-переменных проекта или группы либо во внешнем хранилище. В `.gitlab-ci.yml` и вообще в
  репозитории их нет.
- **Protected**: переменная доступна только пайплайнам защищённых веток и тегов. Все боевые креды делай protected.
- **Masked** (а в свежих версиях ещё и **hidden**): значение маскируется в логе. Маскировка ловит только точное
  значение, после base64, обрезки или форматирования секрет утечёт, поэтому не печатай секреты вообще.
- Тип **File** подходит для ключей и конфигов: в переменной лежит путь к временному файлу с содержимым.
- В лог секреты чаще всего попадают через `set -x`, `env`, `printenv`, `curl -v` и `--debug`-режимы инструментов.

## Краткоживущие креды через OIDC

Статичный ключ в переменной живёт годами и копируется куда угодно. `id_tokens` выдаёт джобе JWT, который облако или
Vault обменивает на временный токен с нужными правами:

```yaml
deploy:
  id_tokens:
    VAULT_ID_TOKEN:
      aud: https://vault.example.com
  script:
    - ./scripts/ci/deploy.sh   # обменивает $VAULT_ID_TOKEN на временный токен Vault
```

В Premium есть ключевое слово `secrets:`, которое делает обмен с Vault за тебя.

## CI_JOB_TOKEN

- Токен существует, пока идёт джоба. Его права совпадают с правами пользователя, запустившего пайплайн, и дополнительно
  ограничены allowlist (Settings → CI/CD → Job token permissions).
- Для container registry, package registry и API разрешённых проектов используй его вместо персональных и проектных
  токенов.

## Доверие к коду и зависимостям

- Пайплайн MR выполняет код из ветки MR на твоих раннерах. Поэтому protected-переменные не попадают в пайплайны
  незащищённых веток, и снимать флаг protected, «чтобы заработало», нельзя.
- MR из форков по умолчанию выполняются в проекте форка. Запускать их в родительском проекте можно только после ревью
  кода.
- Образы фиксируй по digest или неизменяемому тегу, `include` по тегу или SHA. Иначе изменение в чужом образе или
  репозитории меняет твой пайплайн без ревью.
- `include: remote` подключай только из своих и доверенных источников.

## Деплой, подпись, публикация

- Деплой, подпись сборок и публикация запускаются только на защищённых ветках и тегах.
- Protected environments (Premium) позволяют ограничить, кто может деплоить, и требовать подтверждения.
- Для таких джоб заведи отдельные раннеры с отдельными `tags` и флагом protected: такой раннер берёт джобы только из
  защищённых веток.
- Ключи подписи и сертификаты храни в protected File-переменных или во внешнем
  хранилище, не кэшируй и не складывай их в артефакты.
